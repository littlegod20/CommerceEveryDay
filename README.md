# CommerceEveryDay

A demo e-commerce storefront — kitchen, style, and tech essentials — built as a portfolio piece to walk through with clients. Full catalog, cart, checkout (Paystack test mode), customer accounts with order history, and a small admin panel for managing products and orders.

**Stack:** Next.js 16 (App Router) + TypeScript · PostgreSQL (Neon) via TypeORM · Tailwind CSS v4 + shadcn/ui · Framer Motion · Auth.js v5 (customer auth) · Paystack (checkout) · Docker Postgres for local dev

## Local setup

1. **Install dependencies**

   ```bash
   npm install
   ```

2. **Start a local Postgres** (or point `DATABASE_URL` at your own instance / Neon project)

   ```bash
   docker compose up -d
   ```

3. **Configure environment variables**

   Copy `.env.example` to `.env.local` and fill in the values. See the comments in that file for how to generate each secret. One gotcha worth knowing up front:

   > Next.js expands `$VAR` references when it loads `.env` files. A bcrypt hash is full of `$`, so `ADMIN_PASSWORD_HASH` **must** have every `$` escaped as `\$`, or it gets silently corrupted. `scripts/hash-password.mjs` prints the value pre-escaped and ready to paste — use it rather than hand-copying a hash from elsewhere.

4. **Run migrations, then seed the database**

   ```bash
   npm run migration:run
   npm run db:seed
   ```

   This creates 3 categories, 20 products, and one demo customer account (see below). Re-running `db:seed` is safe — it upserts by slug/email rather than duplicating rows.

5. **Run the dev server**

   ```bash
   npm run dev
   ```

   Open [http://localhost:3000](http://localhost:3000).

## Demo logins

**Customer** (storefront checkout, order history):

- URL: `/account/login`
- Email: `demo@commerceeveryday.com`
- Password: `Demo1234!`

Or register a new account from `/account/register` — checkout requires being signed in, but browsing and the cart work as a guest.

**Admin** (`/admin`, separate route and session from the customer site):

- URL: `/admin/login`
- Username: whatever you set as `ADMIN_USERNAME` (`.env.example` defaults to `admin`)
- Password: whatever plaintext password you hashed into `ADMIN_PASSWORD_HASH` via `node scripts/hash-password.mjs "your-password"`

There's no seeded admin password — it's config, not data, so it never lives in the database or the repo.

**Paystack checkout**: use [Paystack's test card numbers](https://paystack.com/docs/payments/test-payments/) once you've added your own test API keys to `.env.local`. Amounts are charged in USD.

## Why TypeORM (not Prisma)

The brief called for TypeORM specifically. A few implementation notes worth knowing if you're used to Prisma:

- **Decorator-based entities** (`src/lib/db/entities/`) instead of a schema file — the entity class *is* the schema, migrations are generated by diffing it against the live database (`npm run migration:generate`).
- **No implicit query magic.** Relations, joins, and transactions are explicit (`createQueryBuilder`, `dataSource.transaction(...)`), which is more verbose than Prisma's relation queries but keeps the generated SQL predictable — useful for the stock-decrement-on-checkout logic, which needs a real transaction, not an optimistic update.
- **Bundler friction that Prisma doesn't have.** Two real issues surfaced building this that are documented as comments/commit messages where they were fixed, in case they bite you elsewhere: circular imports between related entities (e.g. `Category` ↔ `Product`) crash under Turbopack's stricter module evaluation even though they work fine under plain Node — fixed with type-only imports + string-based relation targets. And TypeORM's Postgres driver does a dynamic `require("pg")` that bundlers mangle — fixed via `serverExternalPackages` in `next.config.ts`.
- **Serverless connection reuse.** `src/lib/db/data-source.ts` caches the `DataSource` on `globalThis` so repeated Lambda invocations (and dev-mode hot reload) don't each open a fresh Postgres connection.

## Deploying (Vercel + Neon)

You'll need your own accounts for Neon, Paystack, and Vercel — this repo doesn't include any live credentials.

1. **Neon**: create a project, copy the **pooled** connection string (ends in `-pooler`, keep `sslmode=require`) into `DATABASE_URL`.
2. **Paystack**: from your dashboard, grab the test-mode public/secret keys for `NEXT_PUBLIC_PAYSTACK_PUBLIC_KEY` / `PAYSTACK_SECRET_KEY`.
3. **Push this repo to GitHub** and import it in Vercel.
4. **Set environment variables** in the Vercel project settings — everything in `.env.example`, with real values. Remember the `\$` escaping rule above for `ADMIN_PASSWORD_HASH` applies in the Vercel dashboard too.
5. **Run migrations and seed against the Neon database** before or right after the first deploy:

   ```bash
   DATABASE_URL="<your neon pooled url>" npm run migration:run
   DATABASE_URL="<your neon pooled url>" npm run db:seed
   ```

6. Deploy. Next.js on Vercel is zero-config — no `vercel.json` needed.

## What's fully implemented vs stubbed

**Fully implemented**

- Product catalog with categories, filtering, product detail pages
- Cart persisted per browser session (cookie-based, works pre-login)
- Checkout via Paystack Inline Popup, with server-side transaction verification (amount is recomputed server-side and cross-checked against what Paystack actually charged — never trusts the client)
- Order confirmation + order history for logged-in customers
- Admin panel (separate auth, separate layout) with product CRUD and an orders list
- Scroll-triggered Framer Motion animations on the hero, section headers, and product/category cards

**Stubbed / intentionally out of scope**

- **Paystack webhook** — verification happens on the client's `onSuccess` callback calling back to the server, not via a webhook endpoint. Good enough for a demo; a production app should also handle webhooks for reliability (e.g. the user closing the tab mid-verification).
- **Guest checkout** — the cart works without an account, but checkout requires sign-in so orders have a stable owner for order history.
- **Tax / shipping cost calculation** — order total is just the cart subtotal.
- **Email receipts / notifications** — none are sent.
- **Password reset** — no flow for a forgotten customer password.
- **Product image galleries** — one image per product, no multi-image/variant support.
- **Pagination** — the catalog is small enough (20 products) that the product grid just renders everything.

## Project structure

```
src/
  app/
    (storefront)/     customer-facing routes — own root layout (header/cart/footer)
    (admin)/admin/     admin routes — separate root layout, no customer chrome
    api/auth/          Auth.js route handler
  components/          organized by feature (product, cart, checkout, orders, admin, auth, layout, motion)
  lib/
    db/                TypeORM entities, migrations, data source
    auth/               Auth.js config + admin session (separate mechanisms)
    cart/, checkout/, orders/, catalog/, admin/   feature-scoped queries + server actions
  proxy.ts             admin route guard (Next.js 16 renamed "middleware" to "proxy")
scripts/
  seed.ts              seeds categories, products, and the demo customer
  hash-password.mjs    generates a .env-safe (pre-escaped) bcrypt hash for ADMIN_PASSWORD_HASH
```
